# Methods in the product's compiled code that keep or read state outside the process's memory:
# files, directories and temporary files, memory-mapped files, named mutexes, semaphores and events,
# pipes, sockets, child processes, unmanaged memory and native calls. Such state is outside what the
# process-state gate can walk, and a second process (another server, the non-interference check's
# fresh process) shares it, so a store kept there without the tenant crosses tenants unseen (critic
# p05 round 12, plant L9: list totals in temporary files; critic p04 round 11, plant SL1: the digits
# last chosen, in a file). Reviewed method by method (the G1 compiled-code gate,
# tests/Erp.Gates.Tests/G1/G1OutsideProcessStateTests.cs): any other method that calls such an API
# fails the gate until reviewed here. An async method's state machine, a lambda and a local function
# count for the method they are written in.
# Format: <Namespace.Type>.<Method>  # reason
Erp.Modules.Identity.Auth.ClientAddresses.Read  # Reads this server's own routing tables (/proc/net/route, /proc/net/ipv6_route: kernel pseudo-files, read-only to the process) once, from the ClientAddresses constructor at start, to learn the gateways every client arrives from behind a published port. The path is a constant; the text is the kernel's, the same for every tenant; nothing is written and no request's or tenant's value reaches the call. The parsed gateways are fixed for the process's life.

Erp.Modules.Reports.Pdf.PdfFontFace..ctor  # Copies an embedded font program (the same bytes for every tenant, from the assembly's resources) into unmanaged memory once for the text shaper, which needs a stable pointer. It holds no request's or tenant's data and is never written after the copy.
Erp.Modules.Reports.ReportEndpoints.PdfFile  # One print request's PDF (a list of 100,000 rows is some 2,000 pages, too large to hold per request in memory) is written to a scratch file whose name is fresh for this call (Path.GetTempPath plus a new 128-bit random Guid), created with FileMode.CreateNew (never an existing file) and FileShare.None, and on Linux unlinked by File.Delete at once (on Windows FileOptions.DeleteOnClose), so only the one open handle reaches the bytes; that handle is streamed as this response's body and disposed with it. No code opens a path it did not create in the same call, no name is kept or reused, and nothing outlives the response, so one tenant's printed rows cannot reach another tenant's request or another process.

Erp.Modules.Attachments.LocalAttachmentStore.SaveAsync  # Writes one uploaded file: the folder is the session's own tenant id (a Guid formatted as 32 hex digits, handed in by the endpoint from ITenantContext) under the configured root, the file name is a fresh Guid made here, created with FileMode.CreateNew and FileShare.None as '<id>.part' and moved to '<id>' when whole; a failed or oversized write deletes the '.part' file. No client name, extension or path reaches the call (the client's file name is only stored as text in the tenant's own row), and the stored key it returns carries the tenant id, so a row can only name its own tenant's bytes (database check ck_files_storage_key).
Erp.Modules.Attachments.LocalAttachmentStore.OpenAsync  # Opens one stored file for reading: the key must be exactly '<tenant 32 hex>/<id 32 hex>' (a generated regular expression, anchored to the end) and its tenant part must equal the tenant of the call, which the endpoint takes from the session; any other key (parent-folder segments, separators, another tenant's key) opens nothing. The path is built from the two parsed hex groups only.
Erp.Modules.Attachments.LocalAttachmentStore.DeleteAsync  # Deletes one stored file by the same rule as OpenAsync (the key's tenant must be the call's tenant and both parts exactly 32 hex digits); any other key deletes nothing. Called after the row's removal is committed, or to clear the bytes of an upload that did not end in a saved row.

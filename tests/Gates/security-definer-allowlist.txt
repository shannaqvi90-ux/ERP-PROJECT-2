# SECURITY DEFINER functions: the only code that reads across tenants. Each needs a reason.
identity.verify_sign_in(p_email text, p_proofs text[], p_source text, p_ip text, p_user_agent text, p_threshold integer, p_window_minutes integer, p_shared boolean, p_pending text, p_approval bytea)  # Sign-in. Without proofs: the hashing parameters (algorithm, cost, salt) of the accounts with the e-mail, or a keyed decoy, never a hash or an id. With proofs (the app's PBKDF2 of the password for each salt): the workspace of each account whose stored hash equals a proof, is active, unexpired and whose client is not paused; every other outcome is recorded in that account's own sign-in history, and a failure is counted under the keyed address and client (identity.sign_in_failures); when nothing matched and the address is paused for the client, one row with only the time the pause lifts, worked out the same way whether or not an account has the address. With p_shared (the app's client is an address many clients share, not a known device of the account), a valid unexpired set-up code still matches while that address is paused; every other answer from a paused client is unchanged. With p_pending and p_approval (round 13: the browser's own pending device and the SHA-256 of the device code made from it for this e-mail), an account whose user or administrator let that code in (users.device_approval_hash, unexpired) counts the attempt as that device, a client of its own, not as the shared address; every other account, and a lapsed approval, is unchanged. Each account's attempt is counted under its own client. Answers nothing on a tenant-bound connection.

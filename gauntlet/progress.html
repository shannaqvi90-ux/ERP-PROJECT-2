Biggest gap
Kernel Money adds base amounts that were already rounded, against the owner-signed rounding rule, so foreign-currency documents can be off by fils

Every module that posts foreign-currency amounts (purchases in USD or EUR, the everyday case for a UAE trading company) will build on the kernel Money type. docs/compliance/vat-rounding-and-currency.md rule 2, signed off by the owner, says: 'Rounding happens once, on the figure that is stated. Lines and tax-category subtotals keep their full precision; the invoice total is rounded to 2 decimals.' The kernel breaks this in two ways. (a) Money.Create rounds each base amount to the fils, and Money.Add sums those rounded amounts (BaseAmount + other.BaseAmount). Example: three lines of USD 1.00 at 3.6725 give 3.67 + 3.67 + 3.67 = AED 11.01, but the rule gives 11.0175, rounded to 11.02. (b) Money.Create throws on any amount with more decimals than the currency's minor units, so a line cannot keep full precision at all. Round 9 reported this and it is still open (round 10 only factored out RoundToMinorUnits). Fix in the kernel before p08 and the ledger build on it: keep line and subtotal base amounts at full precision (or carry the unrounded product), round only the stated total, and have the type report the rounding difference that e-invoices put in 'Rounding Amount'. This is a rule already signed off, so implementing it needs no new human gate.

Biggest gap
A step's 'cause' window still covers time the step only spent waiting, so the page's own timer write is credited to one click. The product can also tell when the clock starts from verify()'s before-the-clock read.

Round 11 judges causation by timing alone. A write counts as caused when it goes out between a step's start and 1 s after its end, or within 1 s of the answer to any request that went out during a step. Three things defeat this. (1) A step's window is [at, at+took], and 'took' includes Playwright's actionability wait. An op.click (or op.scrollTo) on an element that only appears after the page's own timer has sent the declared write covers that write. This is round 10's R2 again, with one click and 0 keys (S1, S1b). (2) The one-link rule accepts any slow answer as the cause. A delay the step arms is refused as a timer (R2b), but the same delay put into a slow back-end answer is accepted (S2). (3) verify() always reads the back end just before op.start(), so the product sees the clock about to start. It can let the page's ordinary poll approve 0.6 s later; one click on plain text then 'causes' it, and the whole run takes 0.47 s (S3). All four are recorded as verified and beat Odoo's follow-approval baseline. Possible fixes: (a) Time a pointer step from the moment its input is dispatched, not from when the operator began waiting. For example, wait for actionability first (a trial click, or a waitFor counted as system wait), then record `at` just before the real click. (b) Require causal evidence. Use Chromium's request initiator (CDP Network.requestWillBeSent initiator stack, or a script stack rooted in a trusted input event handler), not proximity in time. Link through an answer only when the request carrying it was itself caused by the step. (c) Put an unpredictable gap, or a fixed wait longer than REACTION_SECONDS, between the before-clock verify() read and op.start(). Or read verify's before state without a back-end call the product can tell apart. (d) Add S1-S3 as self-tests and mutations. (e) Add a self-test that a step's label never counts as typed text (my mutation C3 survives the whole suite).

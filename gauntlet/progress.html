Biggest gap
A driver can still act uncounted or finish off the clock through the page: async continuations escape the sentinel, and the after-clock freeze does not stop late answers

Round 6 closed the Node side (the sandboxed driver process). The browser side is still open in two ways. (1) Uncounted actions. The sentinel only refuses what the condition does synchronously. Anything it schedules runs after disarm() puts every refused method back: a native `await` (which never calls the patched Promise.prototype.then), `Element.animate().onfinish`, and similar callbacks. A ctx.read or op.waitFor condition can therefore fill fields and click Save with no step counted. The MutationObserver, focus and address checks look only at the synchronous window. (2) Wrong timer. Emulation.setScriptExecutionDisabled does not stop the page's in-flight fetch continuations. A driver can return from run() before the product answers, and verify() can read the page in short ctx.reads until the answer is on screen. The meter misses this: - page reads are not 'repeated back-end reads'; - each pause stays under 1 s; - the slower-first-pass rule needs a gap over 3 s. The harness's own T2b test waits only 0.9 s on a 2 s answer, so it cannot see the freeze fail. Removing freezePages altogether leaves the suite green (mutation M5). Possible fixes: - Run conditions in an isolated world (Playwright's utility world or a CDP isolated context) so page globals and the product's handlers are out of reach. - Or refuse any condition whose source contains async, await, function scheduling or observer constructors, and keep the sentinel armed until the next turn of the page's event loop (check for DOM mutations and requests started after the condition returns, before the next counted step). - Treat any non-GET request, or any DOM change, that starts while no counted step is in progress as an uncounted action. - Make the freeze real: pause the page with Debugger.pause, or abort in-flight responses at the clock and snapshot the DOM there. - Make verify() read a DOM snapshot taken at finish(), not the live page. - Add S1, S2 and T3 as self-tests. Also test that the frozen screen stays unchanged after more than the product's answer time.

Biggest gap
The branch attack only tries branch Z's own ids, never the attacker's own company: branch-owned rows reached through a company-level read or export pass every gate

The branch layer is enforced only in the application (the EF branch filter), so every read that selects by company must apply it. The branch attack (CompanyAttack.RunAsync, Layer.Branch) does two things. It sends branch Z's ids and texts into routes, queries and bodies. It also checks company X's shared records for writes. It never makes the branch-limited attacker read company X's own reports, exports and per-user screens with valid company-X parameters (or with none) and then look for branch Z's markers in the answer. Three one-line plants that skip the branch filter passed every G1 and G2 gate, and each is a real leak on a running build. B3: the company profile report (CSV, PDF, JSON) prints every branch of company X with its phone. B3b: a plain GET of the branch directory report lists every branch. B1: GET /api/tenancy/access/{userId} offers every branch's code and name as options. Only the hand-written module test GrantRulesTests noticed B1. This is the same pattern that failed rounds 3 and 4, a branch rule guarded only by module tests. Every later module's 'by company' report, export or job would inherit the blind spot. For a UAE group that limits a warehouse keeper or branch manager to one branch, that means branch-confidential data (other branches' contacts, and later their stock, sales and costs) can leak through any company-level export with no gate turning red. The fix: in the branch layer, also call every GET (reports and list prints included) as the branch-limited attacker with only valid own parameters. That means no parameters, company=X, and the company-X filters in the list contract. Judge each answer against branch Z's markers, the code and names stored when branch Z was created, so the 'values the attacker sent or stored' exclusion cannot hide them. Then plant-test B1, B3 and B3b as gate self-tests.

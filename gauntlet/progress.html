A task 'of no traceable origin' (a message) counts as the step's when two things hold: the page task just before it was caused, within REACTION_SECONDS, and no uncaused page task ran in between. That guard only looks at the page's own main thread and its workers. Timing that lives outside the thread is invisible to it. W1 shows this with a web socket. Set-up turns on a setting. A role held in one company acts on another company's records: Company manager in ALN-DXB, Read-only in ALN-FZE, changes FZE's company and branches and creates FZE branches while working in DXB

Permissions for a request are the workspace roles plus the roles of the working company. The company scope that RLS enforces is every company the user works in. No tenancy endpoint (companies update and logo, branches create and update, and access update too) checks the permission in the company of the record it touches, and the kernel's SaveChanges guard checks only that the company is in scope. So a group's 'accountant in the Dubai LLC, read-only in the JAFZA entity' (the case per-company roles were built for) can rewrite the JAFZA entity's legal registration (trade licence, TRN, the Arabic-legal-name setting, active flag), its branches, and create new branches in it. Switching to the company where they hold the role is all it takes. The screen offers it too: the FZE form opens with Save while the user works in DXB. G2CompanyRoleTests checks only a user who is working in Y, so every gate passes. Fix: authorise company-owned writes and reads against the grants held in the record's own company, for example a kernel check that every ICompanyOwned row written in a request lies in a company where the declared permission is covered (UserGrants.Covers(permission, companyId)), or narrow the session's write scope to the companies where the permission is held. Add the gate: for every endpoint and permission held only in X, a user working in X who names Y's records (path ids, body companyId) gets 403 and changes nothing. Biggest gap
In the shipped deployment every client has the same address, so five anonymous wrong passwords stop the real user signing in from any new device for 15 minutes, and the sign-in history cannot tell attacker from owner

The README promises: 'Failed sign-ins pause only the client that failed, on that account.' In the one-command deployment the app sees every request from the compose gateway (172.21.0.1 or 172.22.0.1). Only a browser that has signed in to that account before is told apart, by its device cookie. An anonymous attacker who knows an e-mail address sends 5 wrong passwords with no session. After that, the owner's correct password from a new laptop, a fresh browser, or cleared cookies answers 429 with Retry-After 900. The message even says 'from this device'. The set-up-code path is a fresh browser by definition. So a newly invited employee, or the finance manager on a replacement laptop, can be kept out indefinitely at 5 requests every 15 minutes. The administrator's tools cannot help: - The sign-in history and 'Sign-in is paused from 1 address' show the same 172.x address for the attacker's script and the owner's laptop. The user agent is the only difference. - 'Allow sign-in again' lifts the pause for the attacker too. This has been an 'other finding' since round 1. It is now the largest p03 weakness left, because lockout and sign-in history are in this piece's scope and everything else in scope works. Fix: - Make the shipped deployment see real client addresses: put a reverse proxy in compose with ERP_KNOWN_PROXIES set by default, or use host networking for the published port. Show in the history when an address is a proxy or gateway. - Until then, do not let failures from an unrecognised client pause a first sign-in that presents a valid set-up code. - Add a test: a second client with no device cookie, behind the same gateway, still signs in after another client's 5 failures.

Biggest gap
The G1 HTTP attack misses a tenant leak through any parameter that is not an id

The attack sends tenant B values in only a few places. Routes get B's GUIDs and its code. The query string gets fixed names (tenantId, tenant, id, userId, search, workspace). Body uuid fields get B's ids, and B's e-mail goes only to sign-in. Documented query parameters are ignored, and string fields such as email, code or name never carry B's real values. Nothing attacks the two reviewed SECURITY DEFINER lookups through new callers. So an endpoint that ignores the tenant by looking something up by e-mail, code or name passes the whole gate. For an ERP that will soon add contacts, products and documents looked up by code, TRN or e-mail, that blind spot is the main risk. Fix: drive every documented query, route and body parameter from the OpenAPI document with all of B's markers (ids, codes, e-mails, names, canary). Also fail when any endpoint other than auth.signIn and the session resolver calls identity.resolve_login/resolve_session. A related G2 blind spot: no gate checks that user create stays within the caller's grants.

Biggest gap
The permission gate (G2) never sends a request from any client address other than the test server's own, so a kernel rule that trusts loopback callers passes every test

Every G2 matrix, the carrier matrices and every G1 request go through the in-memory test server's client. Nothing in tests/ sets a client address except through X-Forwarded-For in the sign-in throttle tests. So a permission decision that depends on where the request comes from is never tested. Plant P11 in the kernel PermissionAuthorizationHandler passes any signed-in request from loopback, on the reasoning that 'jobs and the reverse proxy on this machine are trusted'. That is a common real shortcut, and the product itself already treats loopback as 'a proxy or development server on the same machine' (ClientAddresses, decision p03-identity-setup-code-from-shared-address). With P11 in place, a user with no roles read every user and role of the workspace. Even so, 135 G2/Rules/SelfTests tests, 74 G1 tests and 107 Identity tests all passed. For a UAE trading company the usual deployment puts nginx or Caddy on the same host, and then every browser request reaches the app from 127.0.0.1. One such rule would hand every clerk the owner's rights to price lists, payroll and VAT returns, and no gate would notice. Fix it inside G2: run the deny-everything, grant-exactly-one, own-id and carrier matrices from a set of client addresses as well: loopback (127.0.0.1 and ::1), the compose gateway, a configured proxy with and without X-Forwarded-For, a declared shared address and an ordinary client. A startup filter that sets HttpContext.Connection.RemoteIpAddress per client is enough, much as CriticR13Proof's LoopbackClients does. Add a self-test that plants the loopback rule and must be caught, and a ratchet count for the client addresses checked.

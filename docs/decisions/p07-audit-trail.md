# p07 — Audit trail: reading the trail p00 writes

Date: 2026-10-24. Piece: p07-audit, round 1. Status: accepted.

## What existed (p00) and what this piece adds

**Existed** (`docs/decisions/p00-foundation-audit-trigger.md`): the kernel-owned, tenant-owned
table `audit.entries` (row-level security forced), written by the `audit.capture()` row trigger
that `TenantSql.ProtectTenantTable` attaches to every tenant table, in the same transaction as the
change, field by field (`{"column": {"old": …, "new": …}}`), with the actor and correlation id
from the transaction's settings, secrets redacted and high-churn columns left out. The application
role may `SELECT` and `INSERT` its tenant's rows, never `UPDATE`, `DELETE` or `TRUNCATE` them. The
audit rule gate checked that every tenant table carries the trigger and that API and raw-SQL writes
leave rows.

**Added**, without a second store:

- **One store, more columns** (kernel migration `AuditTrailReading`): `uid` (a uuid per row, for
  list paging and links), `record_type` (`schema.table`, generated), `record_label` and
  `record_label_ar` (what the record was called when it changed, so the trail names a record
  after it is renamed or deleted), `record_code` (its e-mail or code, so a user's changes are found
  by their sign-in and a company's by its code), `record_company_id` and `record_branch_id` (the
  record's company and branch) and `fields` (the recorded field names, generated by
  `audit.field_names(changes)`), with the indexes the log needs: `(tenant_id, occurred_at, uid)`,
  `(tenant_id, record_type, record_id, occurred_at)`, a unique `(tenant_id, uid)`, GIN on `fields`,
  trigram GIN on both labels and the code.
- **Capture, second version** (`KernelSql.CaptureFunctionV2`): fills the new columns; records
  tenant-defined custom fields (a JSON object column named `custom_fields`, p09's contract) field
  by field as `custom_fields.<key>`, exactly like the record's own columns, so a custom field's old
  and new value are in the trail from the day p09 adds them; takes the time from
  `clock_timestamp()` so the changes of one transaction keep their order.
- **Company layer**: a RESTRICTIVE `FOR SELECT` policy `audit_company_scope`
  (`record_company_id IS NULL OR erp.company_allowed(record_company_id)`), so a row about a record
  of a company is read only inside the reader's company scope, as the record itself is. It is on
  reads only: the trigger must insert rows for every company a statement reaches (a foreign-key
  cascade bypasses row security), and the trigger uses no `RETURNING`, so no SELECT policy can make
  a business write fail. The column is not called `company_id`, so the trail is not taken for a
  company table (which would need the company write policies and refuse the trail's own inserts).
- **Registry of kinds of records** (`Erp.Kernel.Audit.AuditRecordType`,
  `ModuleBuilder.AuditedRecord`): each module registers its audited tables with a name (web
  string), the permission that reads them and the record's web address. Identity, tenancy and lists
  register their 15 tables.
- **Audit module** (`src/Modules/Audit`, no tables): the audit log list on p05's list framework
  (`/api/audit/log`), one change with its stored values (`/api/audit/log/{id}`), a record's history
  (`/api/audit/records/{id}?type=<schema.table>`), printing and export through p06's report
  framework (`/api/reports/lists/audit.log`, PDF/CSV/XLSX, English and Arabic). The log's rows are
  kept small (one change line in the request's or the document's language, at most 200 characters);
  the change panel reads the stored values.
- **Screens**: every record form (p06's `RecordForm`) shows the record's latest change under its
  heading (who, when, each field's old and new value) and its whole history below the form on
  demand (toolbar History, Alt+Y, the command palette), through a new kernel extension slot
  (`record` in `kernel/extensions.ts`) the audit module fills; `RecordForm` now requires the
  `record` it shows (type and id), so the compiler refuses a form without its history. A screen that
  shows a record to a reader without a form (the workspace page) uses `RecordPanels`. The audit log
  screen (`/audit/log`, G then L; G then Y went to the currencies screen of p08, merged first) opens a change in the side panel with every field and links to
  the record and to the record's history.

## Who may read what

- The log, a change and a record's history need `audit.log.read`; on top of it each kind of record
  needs its own read permission, a record of a company needs it in that company, and in a company
  where the reader may work in only some branches, a branch they may not work in and every row of
  it (its `branch_id`) does not exist for them (`AuditReader.VisibleAsync`): the history of a record
  tells everything it ever held, so the trail never shows more than the record does (the sign-in
  sessions and passkeys need the sign-in history's permission, which the read-only role lacks).
  Row-level security (tenant, and the company policy above) is the first layer, the application
  filter the second. The history panel on forms is offered to readers of the trail only (the
  extension names `audit.log.read`). One route for every record's history, not one per kind under
  that kind's permission (built first, measured): sixteen routes cost the isolation and permission
  gates, which attack every route, hundreds of processor seconds of the verify's limit.
- Nobody may change the trail through the product (there is no write endpoint), and the database
  refuses the application role every `UPDATE`, `DELETE`, `TRUNCATE`, disabling or dropping a
  table's audit trigger, replacing the capture function, dropping the company policy, turning row
  security off and `session_replication_role` (G1 append-only gate, made stricter here).
- Not done: refusing the application role direct `INSERT`s into `audit.entries` (forged rows).
  It would need the capture function to be `SECURITY DEFINER`, and the reviewed maximum of such
  functions (`g1.securityDefinerFunctions`, 2) is reached; a BEFORE trigger that refuses inserts not
  made by a trigger can be got round with a temporary trigger function. The product has no path
  that inserts into the trail but the trigger.

## Why these shapes

- **One row per change, the fields as an array**, not one row per field: a table of field rows
  would be a tenant table without the audit trigger, and the reviewed maximum of such exemptions
  (`rules.auditExemptTables`, 2) is reached; and every write would cost N inserts. The field filter
  (`fields eq 'email'`) is served by the list framework's new multi-value choice column (a choice
  column bound to `string[]`: `eq` holds the value, `ne` does not, `in` holds one of them; not
  sortable or groupable), translated to PostgreSQL array membership.
- **Field names live in the audit screens' strings** (`audit.field.<column>`), one name per column
  name across modules, and the audit gate requires an English and an Arabic name for every column
  the trigger records of every audited table: a new table or column fails the gate until its
  history reads in both languages. The log's field choices are those names (embedded at build
  time, `AuditTexts`).
- **Names of records referred to by id** (a user's role, a branch's company) come from the trail
  itself (the latest label of that record id), among the kinds of records the reader may read.
- **People** are named through identity's public contract (`IUserDirectory`); a person no longer in
  the workspace is "Former user", work the system did by its kind (demo data, background job,
  system).
- **Arrow-free change texts**: "E-mail: from a to b" in English, "من … إلى …" in Arabic; the report
  gate refused U+2192, which no embedded font prints.

## Gates (written before the screens, stricter only)

- Audit rule gate: every audited table is a registered kind of record with a name in both
  languages, a declared read permission and a real screen address; every registered kind is
  audited; every recorded field has a name in both languages (`rules.auditRecordTypesChecked` 15,
  `rules.auditFieldsNamed` 121).
- G1 database: the `audit_company_scope` policy must exist on `audit.entries`, exactly (restrictive,
  SELECT, PUBLIC, the reviewed expression) and nowhere else; the append-only test also refuses the
  trigger and policy tampering above.
- G2: the module's three routes are in the reviewed map `tests/Gates/endpoint-permissions/audit.txt`;
  the log's saved views are reviewed reader writes and write sets (`read-permission-writes.txt`,
  `permission-write-sets.txt`).
- List gates: the index gate and the volume gate now also read the kernel's DbContext (the trail's
  table; the volume gate anchors its rows by their `uid`); the list contract gate checks multi-value
  choice columns (`eq`, `ne`, `in`) and judges a list that grows while it reads (the trail: every
  sign-in of the other gate tests adds a row) on a fixed window of its rows, newest 150 by its
  default time sort; the volume gate matches multi-value choice values.
- G1: the tenant snapshot collects a table's `uid` when its `id` is not a uuid (the trail's rows'
  ids are markers and list answers are checked against them); the company and branch attacks count
  the trail's rows as text a record holds (rows about the victim's records stay the victim's;
  rows about the attacker's own records explain an answer, as do values inside text the attacker
  stored and the attacker's own code change), so the readable history is judged, not skipped.
- G1 HTTP, company, branch and report probes reach the new endpoints automatically (every route,
  the list queries, the printable list); the branch attack found the first version showing a
  branch-limited user the history of a branch they may not work in, fixed by `record_branch_id`.
- Reviewed lists: `KernelSql.cs` pins `search_path` in two more functions
  (`tenant-bypass-sources.txt`), and the module registry's audited kinds are reviewed process
  state (`process-state-allowlist.txt`).
- Module tests (`tests/Erp.Modules.Audit.Tests`): history field by field and paging, the cursor
  refused for another record, permissions per kind, the log's filters and search, names for ids,
  company-limited readers, print and export in both languages, custom fields and company rows at the
  database. Web tests: the latest change and the history panel in English and Arabic, values, keys.

## Comparison task

`who-renamed-user` (gauntlet/compare): find who last changed the name of the user now called a given
name, among the shared dataset's 100,000 users, from what to what and when. Both products track user
names (the reference keeps the name among its users' tracked fields). Set-up renames the user as an
ordinary editor (a task input, the new name, is all its write carries); the record is found by the
name it has now (`finds: 'newName'`) and the old name is what the person finds out. Ours' paths open
the user and read the heading's latest-change line (no extra step); the reference reads the first
message of the form's change log. Measured: ours 3 steps, 2 keys, 1.34 s machine, 8.01 s modelled
human (8.96 s with waits); the reference 6 steps, 4 keys, 3.63 s, 10.07 s (13.32 s). `who-changed-field` (contacts) still waits for p16.

## Cost

The capture trigger computes three labels and two more columns per row (and the generated
`fields` and `record_type`); the demo seed's 100,000 user rows write 100,000 audit rows as before.
The gates are the cost: the audit log is the one list that grows with every write, so the isolation
gates walk thousands of its rows (and 200,000 at demo volume). Measured: the builder's first full
verify (16 history routes, rows with every stored value) used 9,825 processor seconds (dotnet 7,358,
web 2,202, e2e 265) on a loaded machine, against about 7,100 to 7,900 for the integration branch
before; the routes were then cut to one, the rows to one capped line and the reader's filter sent as
parameters. The builder's passing verify at `ef63c837` used 9,561 processor seconds (dotnet 6,737,
web 2,253, e2e 529, timing 42; 5,031 s wall, a busy machine); the run before it at the same code
but for a ratchet value, 8,978 (dotnet 6,358, web 2,092, e2e 528). About 1,000 to 1,500 seconds
under the limit of 10,500 remain for p08 onwards.

## Round 1, after the integrator's two failed verifies of its merge

**The G1 list-answer search words no longer depend on the schema** (shared G1 machinery of p00,
changed here on the lead's routing for this round; p00 is done for now and p08's builder does not
touch these files). Cause, confirmed with targeted runs of the self-test
`The_HTTP_attack_catches_planted_header_route_and_body_leaks` with the words and outcomes logged:
`ListAnswers.QueriesFor` searches for the first 12 distinct first words of `VictimValues.Strings`,
which reads the tenant tables in catalogue order (`audit` sorts first) and 8 values per text
column, so this piece's four new text columns of `audit.entries` (record type, both labels, code)
now fill most of that window. The planted sorted-search memo L11 (`/api/leaky/scroll`) is a
process-wide memo, and the two directions run one after the other: every search the second
direction ("tenant A asks first, tenant B judged") shares with the first (the one-letter searches,
words both tenants hold, "Activity") already holds tenant B's own total from the first direction,
so B is answered right. Only a search for a word that tenant A holds, B does not, and the people
list shows, catches it in the second direction; in the logged run that was one word ("Abdullah",
first 4 rows, judged 0), the 14th candidate of a window of 12 that the attack's own stored values
(`attack-127257`…, different in every run) push in and out. When it fell out, the self-test failed
(the integrator's runs, the builder's runs 3 and 4, two of p08's).

Change (`ListAnswers.OwnWords`, stricter only): every searchable list is also searched, in each
direction, for up to two words taken from the list's own rows: whole words (3 to 15 characters,
never a canary, matched by the fields the list searches for that script) of the search fields of
the asking-first tenant's rows, in the list's own order, found in no search field value of the
judged tenant's rows. They are chosen from what the list shows, not from the schema, so no new
table can crowd them out, and the two directions' words differ by construction (a word of one
direction is found in the other tenant's rows), so the second direction always sends a sorted
search the first never sent. Every query sent before is still sent (the 12 words, the one-letter
searches, the filters and groupings): the change only adds queries. A new blind-spot check: a
sortable list that has such words must have a sorted search for one of them with different true
answers in the two tenants, or the run reports itself blind. Proved with a probe run in which the
12 victim words were removed entirely (`ERP_PROBE_NO_VICTIM_WORDS`, a local change not kept): the
self-test still caught L11 in both directions.

**The latest change under a record's heading no longer widens the form.** The integrator's second
run timed out the comparison health check `open-third-user-keyboard`: the third user's latest
change was a device approval (a 64-character hash, one unbreakable word); the line is kept on one
line (`nowrap`), so the heading block's minimum width became the whole line, the form overflowed,
the list's form-fit effect grew the form to fit and the users list beside it kept one column, so
the third row carried no e-mail and the driver's wait never ended. The line now takes the width its
heading block has and never asks for more (`contain: inline-size`; the heading block grows into the
room beside the toolbar with `flex-grow`, starting at its own width as before, so the toolbar wraps
as it did), and an e2e test saves a 100-symbol word into a role's Arabic name and
checks that the form neither overflows nor widens.

**Secrets are never recorded in clear.** The same screenshot showed the device approval code's
SHA-256 in a user's history. The code is eight symbols from an alphabet of 31 (about 8.5 x 10^11
codes), so its unsalted hash is found again by trying every code. New audit rule gate
`Every_audited_secret_is_redacted_or_left_out`: every column of an audited table whose name says it
holds a secret or its hash (`hash`, `token`, `password`, `salt`, `secret` as a word of the name) is
named in its table's `audit.capture()` trigger, redacted or left out (`rules.auditSecretsChecked`).
It failed on `identity.users.device_approval_hash`; identity migration `AuditRedactsDeviceApproval`
now records it as "[redacted]" (shown "(hidden)"); until when the approval holds stays recorded.
Rows written before keep what they hold (the trail is append-only).
